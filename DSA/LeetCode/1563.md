# 1563. Stone Game V 🔴

**Topics:** Dynamic Programming, Prefix Sum, Interval DP, Memoization

## Intuition

Imagine Alice is playing with a row of stones and repeatedly cutting the row into two parts.

For every cut:

* If the left part has a smaller sum, Alice keeps the left part and gains its sum.
* If the right part has a smaller sum, Alice keeps the right part and gains its sum.
* If both parts have equal sums, Alice can choose either side.

The important observation is that after every move, the game continues on **only one smaller interval**.

So instead of simulating every possible game sequence, we can ask:

> What is the maximum score Alice can obtain if the remaining stones are from index `lo` to `hi`?

This becomes an interval DP problem.

The solution also uses two optimizations:

1. **Prefix sums** to quickly calculate the total sum of an interval.
2. **Pruning** to skip split positions that cannot improve the current answer.

## Approach

### 1. Prefix Sum

The code uses:

```python
prefix = list(accumulate(stoneValue, initial=0))
```

This creates a prefix sum array where:

```text
prefix[i]
```

contains the sum of the first `i` stones.

Therefore, the sum of the interval `[lo...hi]` is:

```python
prefix[hi + 1] - prefix[lo]
```

This gives the initial right-side sum in $O(1)$.

### 2. Memoized Interval DP

The main DP function is:

```python
@cache
def dp(lo: int, hi: int) -> int:
```

It represents:

```text
dp(lo, hi) = maximum score Alice can obtain from stoneValue[lo...hi]
```

If there is only one stone:

```python
if lo >= hi:
    return 0
```

Alice cannot split a single stone, so no more points can be earned.

### 3. Maintain Both Side Sums

Instead of recalculating the sum for every possible split, the code maintains:

```python
lsum = 0
rsum = prefix[hi+1] - prefix[lo]
```

As `mid` moves from left to right:

```python
lsum += stoneValue[mid]
rsum -= stoneValue[mid]
```

So at every split:

```text
[lo ... mid] | [mid + 1 ... hi]
```

we immediately know both sums.

This makes checking every split efficient.

### 4. Left Side Is Smaller

If:

```python
lsum < rsum
```

Bob must throw away the right side.

Alice keeps the left side and receives `lsum`.

Therefore:

```python
lsum + dp(lo, mid)
```

is a candidate answer.

The code contains an important pruning condition:

```python
if best >= lsum * 2:
    continue
```

Since:

```text
lsum < rsum
```

the remaining right side is strictly larger than `lsum`.

The current split can only contribute `lsum`, and the future score from the surviving left interval is bounded by the total value of that interval, which is also `lsum`.

So the total possible score from this split cannot exceed:

```text
2 * lsum
```

If `best` has already reached that value, this split cannot improve the answer.

### 5. Right Side Is Smaller

If:

```python
lsum > rsum
```

Bob throws away the left side.

Alice keeps the right side and receives `rsum`.

The candidate becomes:

```python
rsum + dp(mid + 1, hi)
```

The code uses:

```python
if best >= rsum * 2:
    break
```

Here the `break` is stronger than `continue`.

As `mid` moves to the right:

* `lsum` increases.
* `rsum` decreases.

Therefore, once `best >= 2 * rsum`, moving further right will only make `rsum` smaller.

So no later split can improve the answer, and we can stop checking the remaining splits.

### 6. Equal Sums

If:

```python
lsum == rsum
```

Alice gets to choose which side survives.

Therefore, both possibilities must be considered:

```python
best = max(
    best,
    lsum + dp(lo, mid),
    rsum + dp(mid + 1, hi)
)
```

Since the two sums are equal, both sides are valid choices.

## Example Walkthrough

Consider:

```text
stoneValue = [6,2,3,4,5,5]
```

Initially, for the full interval:

```text
[6,2,3,4,5,5]
```

The total sum is `25`.

The DP tries different split positions.

For example:

```text
[6,2,3] | [4,5,5]
```

The sums are:

```text
left  = 11
right = 14
```

Since:

```text
11 < 14
```

Alice keeps the left side and gains `11`.

The remaining problem becomes:

```text
[6,2,3]
```

The DP recursively solves:

```python
dp(0, 2)
```

For the split:

```text
[6] | [2,3]
```

we have:

```text
left  = 6
right = 5
```

The right side is smaller, so Alice gains `5` and continues with:

```text
[2,3]
```

Finally:

```text
[2] | [3]
```

Alice keeps `[2]` and gains `2`.

The total is:

```text
11 + 5 + 2 = 18
```

The memoized DP checks all useful possibilities and returns the maximum score.

## Code

```python
from typing import List
from functools import cache
from itertools import accumulate


class Solution:
    def stoneGameV(self, stoneValue: List[int]) -> int:
        prefix = list(accumulate(stoneValue, initial=0))


        @cache
        def dp(lo: int, hi: int) -> int:
            if lo >= hi:
                return 0

            best = 0
            lsum = 0
            rsum = prefix[hi+1] - prefix[lo]


            for mid in range(lo, hi):
                lsum += stoneValue[mid]
                rsum -= stoneValue[mid]


                if lsum < rsum:
                    if best >= lsum*2:
                        continue
                    best = max(best, lsum + dp(lo, mid))

                elif lsum > rsum:
                    if best >= rsum * 2:
                        break
                    best = max(best, rsum + dp(mid+1, hi))

                else:
                    best = max(best, lsum + dp(lo, mid), rsum + dp(mid + 1,hi))

            return best

        return dp(0, len(stoneValue) - 1)
```

## Why Memoization Helps

The same interval can be reached through different splitting choices.

For example, several different splits may eventually leave:

```text
[2,3,4]
```

Without memoization, we would solve that interval repeatedly.

With:

```python
@cache
```

the first calculation of:

```python
dp(2, 4)
```

is stored.

Every future request for the same interval immediately reuses the stored result.

This turns the recursive solution into a practical interval DP.

## Complexity

There are $O(n^2)$ possible intervals `(lo, hi)`.

For each interval, the code may examine up to $O(n)$ split positions.

Therefore, the standard worst-case bound is:

**Time Complexity**

$$
O(n^3)
$$

**Space Complexity**

$$
O(n^2)
$$

The $O(n^2)$ space comes from the cached DP states.

The prefix sum array requires an additional $O(n)$ space.

The pruning conditions can significantly reduce the amount of work in practice, but the worst-case complexity remains $O(n^3)$.

## Edge Cases

### 1. Single stone

```text
stoneValue = [4]
```

The condition:

```python
if lo >= hi:
    return 0
```

immediately returns:

```text
0
```

There is no possible split.

### 2. Two stones

```text
stoneValue = [5,3]
```

There is only one possible split:

```text
[5] | [3]
```

The smaller side is `[3]`, so Alice gains:

```text
3
```

### 3. Equal sums

```text
stoneValue = [2,2]
```

Both sides have the same value.

Alice can choose either side:

```text
2
```

So the answer is:

```text
2
```

## Lessons

* When a problem repeatedly splits an array and continues with one remaining interval, **interval DP** is a strong candidate.
* Use **prefix sums** when DP transitions repeatedly need subarray sums.
* Memoization prevents the same interval from being solved multiple times.
* When a split becomes provably incapable of improving the current answer, pruning can reduce practical runtime.
* Because `lsum` increases and `rsum` decreases as `mid` moves right, the right-side pruning can use `break` rather than simply skipping one split.
* A useful pattern for this problem is:

```text
Choose a split
    ↓
Compare left and right sums
    ↓
Determine which side survives
    ↓
Add the best score of that side
    ↓
Use pruning when the split cannot improve the answer
```

The main idea is to combine **interval DP + prefix sums + memoization**, then use the monotonic behavior of the two running sums to avoid unnecessary recursive work.
